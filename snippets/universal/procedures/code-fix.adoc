*Procedure — code:fix*

. Reproduce the bug with a failing test first. This test is the proof the bug exists.
. Run that test against the unmodified code and observe it fail, for the reason the bug describes. A test that was only written, never executed red, is not proof of anything — it may pass by accident (wrong mock, wrong assertion, code path never reached) and give false confidence in the fix that follows.
. Fix the code until the test passes.
. Never fix code without a reproducing test — you cannot verify the fix is correct.
. Before considering the fix complete, re-read the test and ask: does every mock/stub in it actually exercise the real code path where the bug lives, or does it substitute away the exact behavior under test? A mock that returns a fixed value regardless of its input can silently skip the line that matters.
. If the fix makes a previously dead/unreachable branch reachable (a stale selector, a guard that was always false, a condition that never matched): there is no prior working behavior to fall back on, only the one path your new test exercises. Enumerate every other caller/context that will now run through this branch and check each one, in the real runtime if the unit-test harness can substitute away environment-specific behavior (see the platform-specific test-write procedure for what "real runtime" means there) — a fix that is correct in isolation can still corrupt output in a sibling context the test never looked at.
. Before writing the commit message, release notes, or a code comment describing the bug's prior impact ("X was never rendered", "Y always failed"): verify that claim against the actual unmodified behavior (run it, don't infer it from reading the code) — an overstated or understated diagnosis is itself a defect that will mislead the next reader.
. If the fix addresses a reported issue: after pushing, close the issue in the issue tracker with a comment referencing the commit.
