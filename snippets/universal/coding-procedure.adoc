*Coding Procedure*

Before writing any code, identify the task type and follow the corresponding procedure:

*feat — implement new functionality*

. Write a failing test that specifies the expected behavior. The test must fail before you write any implementation.
. Write the minimum implementation to make the test pass.
. Refactor if needed — tests must stay green.
. Never write implementation before a failing test exists.

*fix — correct a bug*

. Reproduce the bug with a failing test first. This test is the proof the bug exists.
. Fix the code until the test passes.
. Never fix code without a reproducing test — you cannot verify the fix is correct.

*refactor — improve structure without changing behavior*

. Run the full test suite first. All tests must be green before you start.
. Check test coverage for the files you intend to change. If coverage is below ~80% on the affected code paths, warn explicitly before proceeding: low coverage means the refactoring cannot be verified safely. Do not block, but make the risk visible.
. Make structural changes (extract method, rename, move class, etc.).
. Run the full test suite again. All tests must still be green.
. If a test breaks, you changed behavior — revert the change or explicitly justify updating the test.
. Never change test logic during a refactor unless the test itself was wrong.

*test:write — verify existing behavior by closing coverage gaps*

The goal is correct code, not just passing tests.
Use the *specification* (issue, docs, method name, contract) as the source of truth — never the current output of the production code.

. Check whether the described behavior is already covered by existing tests.
. Understand the *intent* of the code under test: what should it do, for whom, under which conditions? Read the specification, not just the implementation.
  - If no specification exists (no issue description, no docs, no method contract) and the intent cannot be confidently derived from the code alone: *stop and ask*. State what is unclear and what information is needed before proceeding. Do not infer tests from implementation details alone.
. Write the new test(s) that assert the intended behavior — independently of how the code currently works.
. Run the targeted test class.
  - If all new tests are green: the code matches its specification. Done.
  - If a new test fails: the code deviates from its specification — this is a bug discovery. Do *not* adjust the test to match the actual output. Fix the production code so it fulfills the specification (follow the `fix` procedure for the code change). The test stays as written.
. Never adjust a test to match incorrect production code behavior.
